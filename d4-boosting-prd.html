D4 代练业务需求文档

以 Diablo 4 为首个品牌，覆盖买家前台、买家个人中心、卖家上架、卖家中心与平台租户后台
更新日期 2026-10-15 范围：Game / GamePal & Boosting · Diablo 4 配套：D4 代练 Demo 原型
一句话

标准化商品为主、Custom 为补充的 C2C 代练业务。卖家按小类模板上架标准化代练商品并填写费率卡，买家选好属性后看到同规格的在架卖家，价格由各卖家费率卡自动算出，直接下单；标准化商品覆盖不到的组合或特殊诉求，走 Custom：买家自己出价发布并付款，卖家在 Request List 接单。所有代练订单与其他品类订单在同一订单中心流转，复用现有支付、风控、托管、交付、结算与售后。

OVERVIEW

文档概览

目标、范围、角色与优先级原则。

范围

项内容
首个品牌Diablo 4（S14 苏醒赛季），市场 EU / NA
品类升级 · 副本 · Boss 代打 · 剧情解锁 · 配 Build · Custom（共 6 个大类）
涉及端买家前台（代练页、Custom）· 买家个人中心 · 卖家上架 · 卖家中心 · 平台租户后台
不在本期批量上架、退款惩罚规则、产能权重、递送时长区间 / 价格梯度、Custom 方案 B（选场景）

优先级原则：标准化优先于 Custom

供给侧

启动期标准化商品响应更快

标准化商品是卖家预先上架、可搜索 / 浏览 / 直接下单的存量商品，买家进来就有价格、能立即买。启动阶段卖家少，Custom 需求发出去可能没人接，体验是空的。

需求侧

高频诉求标准化商品都能接住

练级、刷 Boss、刷副本等高频诉求用标准化商品选一下就能买，决策成本低、转化快；标准化覆盖不了的组合诉求是长尾，占比小。

平台可控

质量、合规、SEO 与运营都可控

运营配置品类 / 属性，卖家在框架内上架，价格、合规、质量、SEO 可控，热销数据也便于回流运营；Custom 是自由描述，结构松散、难做 SEO，平台掌控力弱。

竞品

竞品普遍标准化优先

谷歌关键词前十的竞品中，除 G2G、U7BUY 用通用模板外，其余几乎都是标准化优先；C2C 竞品没有做标准化，这是 IGV 该抢的差异化位置，Custom 是 C2C 顺带能做的补充。

依赖关系

Custom 本身依赖标准化：A / C 两种方式都是把标准化小类当积木拼，标准化的品类、属性与建议价是 Custom 实现的前提。

01

业务模式与流程

两条交易链路：标准化商品（主）与 Custom（补充）。

1.1 标准化商品

卖家

上架

选品类 / 小类 → 填详情与服务范围 → 设递送方式、递送时长、费率卡、库存 → 发布。

买家

配置

代练页选品类 / 小类，填属性，选递送方式。

买家

对比卖家

看到同规格在架卖家，价格由各自费率卡算出；可先聊天。

买家

下单付款

立即购买 → 结算 → 款项托管。

双方

交付结算

卖家交付 → 买家确认收货（或超时自动确认）→ 放款。

1.2 Custom

买家

发布需求

A 组合服务或 C 描述需求，自己出价，设期望完成时间与有效期。

买家

发布即付款

生成正式订单，过支付风控，款项托管。

卖家

接单

需求出现在 Request List；第一个确认接单的卖家锁单，需求从列表消失。

卖家

交付

组队陪同或上号代打，走现有递送与验收。

平台

结算

买家确认或超时自动确认 → 放款给接单卖家。

未接单分支

买家在 My Requests 主动取消，或超过报价有效期无人接单 → 订单「交易已取消」并原路全额退款。

通用公式

买家前台 · 代练页

Diablo 4 → Boosting 页：选品类、配置、选递送方式、对比卖家、下单。

3.1 页面结构

区域内容
页头面包屑 Home › Diablo 4 › Boosting；同品牌切换 Boosting / Accounts / Items / Top-Up；信任条：iGV 担保、Trustpilot 评分、标准化即买、不交号优先

货服打通同目标也可直接买：装备 / 材料 → Items，成品号 → Accounts，金币 → Gold

3.2 卖家列表

  • 顶部可折叠的「请求详情」：品类、小类、递送方式、平台、备注。
  • 列表为同规格所有在架卖家，按价格升序，最低价标 LOWEST；每行展示卖家名、保证金认证、好评率与评价数、在线状态、递送时长、价格、Chat、Buy Now、卖家说明（可展开）。
  • 价格 = 该卖家费率卡按买家所选属性算出的结果。
  • 底部兜底：「没有满意的？发布自定义需求，自己出价，卖家来接」。

3.3 递送方式的展示位置

建议 · 前置展示，不作关键属性

递送方式作为配置流程里一个独立的必选项前置展示（与属性并列、在查看卖家之前选定），不进入关键属性，也不参与计价。理由：① 它不影响价格，放进属性会和计价属性混在一起；② 它决定账号安全档，买家需要在看价格前先做选择；③ 卖家支持的递送方式不同，选定后可用于过滤卖家列表；④ 关键属性用于 SEO 与商品结构，递送方式不属于“服务内容”。

订单侧：递送方式写入订单「递送信息」，与备注、递送属性信息一起展示给卖家。

3.4 递送方式不影响价格的依据

来源结果
竞品核对（6 家）Overgear、Skycoach、BoostingFactory、Boosteria、BoostHive、U7BUY 均不按递送方式区分价格；U7BUY 上的卖家在通用描述里列出多种递送方式并注明价格不变
卖家访谈（4 位）3 位认为有区别（组队陪同更贵），1 位认为不影响；但多位卖家提到实际几乎都是组队，欧美买家普遍排斥给号、上号代打很少见
影响

本期递送方式不影响价格，与竞品一致；由于实际订单绝大多数是组队陪同，前台默认选中「组队陪同」。卖家对组队更贵的感受，可在费率卡定价里自行体现；若后续上号代打占比上升、卖家集中反馈需要差价，再评估开放按递送方式设置差价。

04

买家前台 · Custom

代练页最后一个大类。两种发起方式，最终落到同一套“组合明细”数据，出价、发布、接单逻辑一致。

4.1 两种方式

A · 组合需求

自由度较高

从标准品类里逐个添加服务并配置，也可一键带入常用组合（如“赛季开荒一条龙”）。结构化，可给组合建议报价。

C · 描述需求

自由度较高

买家用一句话描述，系统识别成结构化服务供确认；需要组织语言，识别结果可能不匹配，提示可切回 A 调整或写进备注。

方案 B 不做

选场景（平台预置场景 + 填空）对平台要求高，不一定贴合买家诉求。

4.2 字段与顺序（A；C 以“描述需求”替换“组合服务”）

#字段规则
1赛季 / 模式必选
2平台必选：PC / PS4/5 / Xbox
3组合服务至少 1 个服务；每个服务展示其配置项与单项建议价；可移除
4你的报价必填，美元；有组合建议报价时默认填入建议价中位数 × 0.92，可修改
5组合建议报价见 4.3 规则；仅作出价参考
6代练需求备注 / 要求可选，自由文本
7期望完成时间数值 + 单位（小时 / 天）
8报价有效期24 小时 / 3 天（默认）/ 7 天；到期无人接单自动取消并退款

递送方式在右侧卡选择，规则同标准化商品。主按钮为「发布需求并付款」。

4.3 建议报价规则

  1. 单项建议价 = 该服务在架卖家建议价区间；该服务没有任何卖家报价时，显示“暂无卖家报价 · 不展示建议价”。
  2. 组合建议报价 = 各服务单项建议价加总；组合中只要有 1 个服务没有建议价，就不展示组合建议报价，并提示“有服务暂无卖家报价，请自行出价”。
  3. C 方式在识别结果确认后，按同样规则展示建议价。

4.4 文案方向

位置EN中文
标题Custom request · combine services or describe it自定义需求 · 组合购买或自由描述
说明Combine several standard services into one request (we suggest a price when sellers have listed them), or describe what you need in one sentence. You set the price; sellers take the job.把多个标准服务组合成一个需求（有卖家报价时给出组合建议价），或用一句话描述你的需求。由你出价，卖家接单。

05

买家个人中心

My Requests 只管需求；所有订单操作都在 My Orders。

5.1 My Requests（我的需求）

状态展示操作
等待卖家接单需求编号、发布时间、需求有效期至、属性 chips（赛季、平台、递送方式、各服务）、需求要求 / 备注、出价（已付款）、期望完成时间取消需求 → 交易已取消，原路全额退款
卖家已接单同上，另展示对应订单号查看订单 → 跳转 My Orders 对应订单
已取消 · 已退款同上重新发布

Tab：全部 / 等待接单 / 已接单 / 已取消。My Requests 只承载 Custom 需求；标准化商品直接下单，不产生需求。

5.2 My Orders（我的订单）

  • 代练订单与其他品类订单放在一起，没有区别；Tab 沿用：待付款 / 待交付 / 待收货 / 待评价 / 已完成 / 退款售后 / 全部。
  • 操作按状态沿用现有：待交付（申请退款、订单详情）、待收货（申请退款、订单详情、确认收货）、待评价（评价）、已完成（再次购买）、退款售后（退款详情）。
  • Custom 订单被接单后在这里出现，退款、评价等操作都在这里进行。
06

卖家上架

单个上架，三步完成；小类决定第三步加载的费率卡模板。

6.1 三步流程

STEP 1

商品类型

Boosting · Diablo 4 · 大类 / 小类；展示佣金（15%）。

STEP 2

商品详情

标题（≤144 字）、商品图（图 <5MB、视频 <20MB）、商品描述；服务范围：勾选可服务的属性值（赛季模式、职业、平台等，按小类不同）。

STEP 3

交易、递送与定价

递送方式、递送时长、费率卡与实时预览、库存、质保期、上架有效期。

结论

现有三步上架流程卖家能看懂、会用，维持单个上架。新增需求：小类属性与枚举值由平台运营配置，可随赛季内容更新（如新 Boss、新难度、新活动），卖家上架时自动加载当季属性。

6.3 第三步字段规则

字段规则
递送方式 *多选：组队陪同（不交号）/ 上号代打；只决定账号安全档，不影响价格
递送时长 *固定值：数值 + 单位（分钟 / 小时 / 天）；向买家展示为参考，不作超时判罚依据
费率卡 *按小类加载模板。升级类：卖家自定义等级段（可增删段，可一键套用平台推荐分段），必须从起点连续覆盖到上限、无缺口无重叠，否则报错不可发布；组合包的每张组成卡都需闭合
属性系数对 Step 2 勾选的每个属性值设系数（加价或乘数），平台给默认值
实时预览卖家选一组属性即时看到算价结果与市场价格带对比
库存 *总库存（必填）、库存报警值、最低购买、最大购买；与现有商品一致，卖家自述，不作真实管控
质保期 *7 / 15 / 30 天；质保期越长排名越高，收益在质保期结束后释放
上架有效期 *30 / 60 天；期内无成交或未更新将暂时下架

6.4 批量上架：本期不做

问题说明
表结构各代练小类至少有 2–3 个不通用属性；合到一个 sheet 列数过多、大量空格，只能拆多 sheet
投入产出倒挂现有批量适配“多行 × 少参数”，代练是“少行 × 多参数”；D4 目前 6 个小类的代练商品约 20 个，批量省力有限，出错和理解成本更高
失去实时反馈单个上架从 Step 2 到 Step 3 能帮卖家理解要填哪些属性、价格参数与属性的关系，并实时预览算价；批量表格里这些都丢失，填错要等错误报告逐个往返修改
技术不确定多 sheet 需单独命名；新增小类时模板是自动新增还是重做，方案不可确认
结论

批量功能投入产出比低，模板实现与现有改动较大，卖家填写理解成本比单个上架高太多，本期维持单个上架。

07

卖家中心

Request List 接 Custom 需求；My Orders 与其他品类合并；My Listings 可查看商品详情。

7.1 Request List（需求列表）

  • 只展示未被接单的 Custom 需求；被任一卖家接单后不再出现在列表，侧栏计数同步减少。
  • 卡片：发布时间、订单号、聊一聊、状态（可接单 / 即将过期）；商品名 + 属性详情；递送信息（代练限时、递送方式、需求要求、备注）；买家报价；报价有效期剩余时间；操作「接单」「聊一聊」。
  • 接单前不展示账号等递送属性明细，接单后才可见。
  • 点「接单」弹确认窗：成交价、按商品分组的属性、限时、要求与备注；确认后订单进入 My Orders，开始计时。

7.2 My Orders（我的订单）

  • 代练订单与其他品类订单合并，功能按钮一致；Tab：待发货 / 待买家收货 / 确认收货 / 已完成 / 退款售后 / 全部。
  • 卡片：时间、订单号、买家、订单状态、事件日志；商品 + 属性详情；递送信息；金额；备注（交付进度、临期提醒、争议原因）；操作按状态（发货、退款详情等）。

7.3 订单信息展示

模块规则状态
属性详情点 Attributes detail 弹窗；普通订单平铺属性；组合包 / Custom 带入多个组合时，按每个标品的商品名分组，组下展示对应属性，共用属性（赛季、平台、职业等）置顶且不重复已定

7.4 My Listings（我的在售）

  • 列表：商品名、品类 · 小类、起价、库存、递送时长、状态、操作（查看详情 / 编辑）。
  • 查看详情：关键属性 / 服务范围 → 价格设置（费率卡）→ 交易与递送（递送时长、库存）→ 商品描述。
建议 · 费率卡不作关键属性

费率卡（计算器参数）是卖家的定价规则，不是服务内容，不放进关键属性；在商品详情里作为独立的「价格设置」模块展示。订单侧只展示买家所选属性值与成交价，不展示费率卡本身。

08

租户后台 · Custom 需求落地

不新增需求列表、不新增字段、不新增状态、不新增 Tab；Custom 需求从下单那一刻就是一笔正式订单。

8.1 落地方式

  1. 预置商品：Custom 的商品信息用计算器提前配置好，由代练自营账号预先上架单位商品，价格统一 $1.00。
  2. 下单：买家出价 $10 → 下单到自营单位商品，数量 = 10，订单金额 = 10 × $1 = $10，生成订单号 + 母单号。
  3. 未接单期间：卖家店铺 / 卖家 ID / 卖家邮箱三列填代练自营账号（代练自营 · 90000000001 · boosting.self@igv.com）。
  4. 接单：订单过风控后，订单所属卖家可修改；第一个接单的卖家锁单，三列改写为实际卖家，佣金按品类“代练”重算。
  5. 交付与结算：走现有递送 / 争议 / 验号流程，买家确认或超时自动确认后放款，进结算单。

8.2 状态映射（沿用订单列表现有四种）

环节订单状态卖家三列递送状态资金买家侧
提交需求待支付代练自营—未收款待支付
支付未完成（风控审核中）代练自营—已收款 · 风控中支付确认中
待接单未完成（等待接单）代练自营—托管中等待卖家接单
卖家接单未完成（已接单）改写 → 实际卖家待发货托管中卖家已接单
交付 / 验收未完成（交付中）实际卖家已发货托管中代练进行中
完成 / 结算已完成实际卖家已完成放款 / 结算已完成

订单列表中 Custom 订单以底色区分，品类为 Game / GamePal & Boosting / Custom。

8.3 取消分支（统一为“交易已取消”）

  1. 未支付超时 → 自动取消（无退款）。
  2. 支付风控拒绝 → 取消 + 原路退款。
  3. 超过报价有效期无人接单 → 自动取消 + 全额退款。
  4. 买家在 My Requests 主动取消（未接单）→ 取消 + 全额退款。

以上情况卖家三列仍为代练自营；退款手续费按已定规则由平台承担。

待定 · $1 单位商品的金额精度

① 币种换算：单位商品定价 1.00 USD，买家按 EUR / GBP 等本币支付，换算后难以正好落在整数美元；② 总金额非整数：数量只能是整数，$52.50、€48.37 这类出价无法用 1.00 × N 精确编码，计算器算出的组合报价也常带小数；③ 牵连优惠改价尾数、退款金额与结算佣金取整。需对照此前的绑定设计规则确定：出价强制取整、调低单位商品单价（如 $0.01），或沿用现有换算规则。

09

递送时长 · 库存 · 接单产能

三个字段的定位，以及真实接单能力如何控制。

9.1 递送时长

  • 本期采用固定值：卖家为商品填一个时长，买家在卖家列表与详情看到这个值。
  • 定位为参考、非承诺，不作超时判罚依据；Custom 的时间约束由买家填写的期望完成时间承担。
  • 备选形态保留为后续演进：区间（最早 ~ 最晚，卖家沟通中更倾向）与按下单金额的阶梯固定值（卖家认为对买家不友好，且价格随赛季波动需频繁修改）。
卖家访谈

卖家普遍认为严格限制递送时间意义不大：实际耗时受买家影响（有组队客户刷到一半去睡觉、第二天继续）；递送时间本就是预计值，卖家会按买家要求放大，分得太细反而麻烦；也有卖家认为可按订单大小给不同时长，但买家并不很关心。这些反馈支持本期用固定值。

9.2 库存

  • 卖家自主填写，与现有商品一致；卖家普遍填充足库存而非真实库存，库存数字不作真实管控。
  • 访谈中卖家表示库存“让卖家自己看情况填即可”，或不清楚如何设计、但自有打手资源充足，与本方案一致。

9.3 接单产能

  • 沿用平台现有「卖家接单自运转规则」：按近 30 天业务与卖家表现动态约束在手订单量，未完成代练订单数达阈值即关闭曝光。代练作为新品牌品类接入，一单一计。
  • 产能权重方案（按递送时长区分长短单、按权重占用产能）暂不考虑，后续有需求再优化。
