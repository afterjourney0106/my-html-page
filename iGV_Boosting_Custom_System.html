方案说明 · Custom 买家需求如何落进现有体系
Custom 是买家先发需求、卖家再来接的反向链路,和现有「先商品 → 后订单」正好相反。
买家在发布需求时就已完成支付并通过支付风控 —— 能进到我们系统里的需求,资金已经在托管中,不存在"发了需求不付款"的情况。
方案乙的做法:需求单独建一个域;卖家接单的那一瞬间,由系统生成一个隐藏的「影子商品」来承载交易参数,再把已托管的这笔钱挂到新生成的订单上。
结果是 —— 订单、托管、结算、退款、争议、理赔全部零改动,金币等其它业务完全不受影响。

改动集中在需求侧,商品与订单主干几乎不动。

页面改动程度具体改了什么

2一条需求的完整流转

支付发生在最前面;前四步在需求域完成,第五步之后完全走现有订单状态机。

  1. 买家在前台填完需求 → 先付款。走现有收银台与支付风控,支付成功且风控通过才继续。
  2. 需求进入我们的系统,资金同时进入托管。系统做内容机审:低风险直接进接单大厅(待接单),命中风险规则则转人工(审核中)。
    因此需求列表里不存在「待支付」这种状态 —— 没付款的需求根本进不来。
  3. 运营在需求列表处理「审核中」的需求:通过放进大厅;或取消掉违规需求,系统原路退款。
  4. 卖家在接单大厅看到需求并接单 → 需求转为已成交,同时从大厅下架、其余报价自动置为未选中。
  5. 系统在同一个事务里做三件事:生成影子商品(隐藏、不上架)、生成订单并把已托管的资金挂到该订单上、把需求锁定。订单生成即为已支付,直接进入待交付。
  6. 之后的待收货、已完成、退款、争议、理赔与普通订单完全一致。

3钱在哪一步动

资金只在两个时点变动:发布时进托管,结束时要么给卖家、要么退买家。

时点资金动作需求 / 订单状态
买家发布需求收款并进入托管(走现有收银台 + 支付风控)支付失败或风控拦截 → 需求根本不进系统;成功 → 审核中 / 待接单
运营取消需求原路退款已取消 · 资金状态转为已退款
买家撤回需求原路退款已取消 · 资金状态转为已退款
有效期到期无人接单自动原路退款已过期 · 资金状态转为已退款
卖家接单托管资金挂到新生成的订单,不重复收款需求已成交 · 订单直接是已支付 / 待交付
买家确认收货托管资金放款给卖家(扣佣金)订单已完成 —— 与普通订单一致
已定规则 ①　退款手续费由平台承担。三种退款情形(运营取消 / 买家撤回 / 到期无人接单)都全额原路退回,支付渠道不退的手续费平台吸收并单独记账,不从买家退款里扣。
理由:运营主动取消违规需求时若还要扣买家手续费,必然引发客诉;而买家撤回与到期退款的金额通常不大,统一规则比分情况处理更省事、也更少纠纷。

因为钱在最前面就收了,卖家不存在"接了单买家不付款"的风险,接单大厅也不会被没有支付意愿的需求淹没 —— 这是这套流程相对"接单后付款"最大的好处。

4运营在需求列表能做的操作

批量操作放在筛选区,和已选商品的「上架 / 下架」同一个位置和用法。

操作对哪些状态生效结果
通过仅「审核中」转为待接单,进入接单大厅,状态下方标注租户人工审核通过
取消「审核中」「待接单」转为已取消,立即从大厅下架,并原路退款给买家,资金状态转为已退款;状态下方标注租户手动取消
勾选框仅上述两种状态可勾已成交 / 已过期 / 已取消的行勾选框禁用(无可执行操作)
点需求编号全部打开需求详情:需求信息 / 需求要求 / 备注 —— 这三块是会转成商品属性与订单数据的内容

没勾选就点按钮、或勾选中没有可操作的行,都会给出明确提示;执行前有二次确认并显示条数。

已定规则 ②　需求发布后不允许改价、不允许修改内容。因为钱在发布时就已收取,任何改动都会牵出补差价或部分退款。买家如果要调整,只能撤回(全额退款)后重新发布。
因此需求列表与需求详情都没有编辑入口,运营侧同样不能代改 —— 只有「通过」和「取消」两个动作。
